# Дизайн: нова логіка архівування KB

**Дата:** 2026-07-27
**Сфера:** скіл `release-notes-tracker`, структура `docs/kb/categories/`

## Контекст і проблема

Поточна логіка ротації (Step 6.5 скіла) створює снапшот робочого файлу в `rotated/<cat>_v<X>.md` щоразу, коли файл перевищує 200 рядків, і прибирає з активного файлу передпередню версійну секцію. Це призводить до:

1. **Дублювання** — `rotated/cli_v2.1.206.md` і `rotated/cli_v2.1.207.md` на 95% збігаються (базові + спільні версійні).
2. **Розпорошеної історії** — жоден файл не містить усієї історії категорії; записи 2.1.205 лише в `cli_v2.1.206.md`, 2.1.207 — лише в `cli_v2.1.207.md`.
3. **Безсилої ротації** для `windows.md` (усі секції базові, не ротуються — файл лише росте) та для `cli.md` (базові самі >200 — ротується щорелізу без зменшення).
4. **Автоматичності** — архівування запускається за порогом під час обробки релізу, без контролю користувача.

## Цілі

- Один архівний файл на категорію за точку архівування, що містить повну (кумулятивну) або прирісну історію.
- Архівування лише за явною командою користувача, не автоматично.
- Робочий файл після архівування починається з нуля (notes наступних версій).
- Міграція існуючого стану до 2.1.207 одним кроком.

## Зафіксовані рішення

1. **Базові записи (версія `—`) теж йдуть в архів.** Робочий файл після архівування не містить базових секцій — починає з нуля.
2. **Кілька архівів по точках:** перше архівування категорії створює кумулятив (всі notes від початку до X), наступні — приріст (prev+1 … X). Разом архівні файли + робочий = повна історія без дублювання.
3. **Мігрувати зараз до 2.1.207** для всіх 12 категорій: створити `archived/<cat>_v2.1.207.md`, очистити робочі файли, видалити `rotated/`.
4. **Підхід 1:** логіка інтегрована в скіл `release-notes-tracker`; міграція — разовий крок скриптом.
5. **Вигляд порожнього робочого файлу** (варіант A): заголовок + блокquote з посиланням на архів і позначкою активного вікна.

## Дизайн

### 1. Структура файлів

- **`docs/kb/categories/<cat>.md`** (робочий) — notes «активного вікна» (від версії після останнього архівування +1 до актуальної). Після архівування до X лишається лише заголовок + блокquote (без секцій і записів), наповнюється notes X+1 у версійних секціях `## <Section> (X+1)`.
- **`docs/kb/categories/archived/<cat>_v<X>.md`** — архівний файл, один на категорію за точку архівування.

### 2. Шаблон порожнього робочого файлу (після архівування до X)

```markdown
# <Заголовок категорії>

> Архів (notes до X.Y.Z): [archived/<cat>_vX.Y.Z.md](archived/<cat>_vX.Y.Z.md)
> Тут — notes починаючи з версії X.Y.(Z+1)
```

Далі файл порожній; нові notes додаються у версійні секції `## <Section> (X.Y.(Z+1))` тощо.

### 3. Команда архівування

Текстова в чаті: `заархівуй <категорію|все> до <версії>`, де `все` = усі 12 категорій. Обробляється секцією «Архівування» скілу `release-notes-tracker`. Під час звичайної обробки релізу ніяких перенесень — лише додавання notes у робочий файл.

### 4. Логіка архівування (для кожної категорії)

1. Зібрати з робочого файлу всі notes ≤ X (базові з `—` трактуємо як найстаріші, теж ≤ X).
2. Визначити, чи це перше архівування категорії (відсутній будь-який `archived/<cat>_v*.md`):
   - **Перше:** створити `archived/<cat>_vX.md` = кумулятив (заголовок + блокquote + базові секції + всі версійні секції до X, відсортовані за версією).
   - **Наступне:** створити `archived/<cat>_vX.md` = приріст (заголовок + блокquote + версійні секції prev+1…X).
3. Очистити робочий файл до шаблону (п. 2).
4. Оновити `meta.md`: `archived.<cat> = vX`.

### 5. Пошук

Як раніше — `Grep(pattern, path="docs/kb/categories/")` шукає по робочих + `archived/` одночасно. Повна історія = сума архівних файлів + робочий.

### 6. Міграція до 2.1.207 (разовий крок, скриптом)

4 категорії ротувались з очищенням робочого файлу (cli, core, settings, skills-agents) — їхні робочі файли мають лише базові + поточну версійну, старі версійні розпорошені снапшотами. Решта 8 (env-vars, hooks, keybindings, mcp, plugins, sdk, vscode-ide, windows) — робочі файли вже містять усю історію: 7 з них не ротувались взагалі, а windows ротувався без очищення (усі його секції базові, а базові не ротуються).

Тому міграція двох типів:

- **Категорії БЕЗ об'єднання (8):** `archived/<cat>_v2.1.207.md` = копія робочого файлу (він уже кумулятив). Робочий → порожній шаблон.
- **Категорії З об'єднанням (4 — cli, core, settings, skills-agents):** `archived/<cat>_v2.1.207.md` = об'єднання всіх `rotated/<cat>_v*.md` + робочого файлу з дедуплікацією:
  - базові секції взяти з найновішого джерела (робочий файл має найактуальніші базові);
  - версійні записи дедуплікувати по (ідентифікатор + версія); при конфлікті (однаковий ідентифікатор+версія з різним описом) брати запис з найновішого снапшота;
  - відсортувати версійні секції за версією.
  Робочий → порожній шаблон.

Після міграції: видалити всю папку `rotated/` зі снапшотами.
