# Release Notes Tracker

Incrementally maintain a modular knowledge base of Claude Code features.

## ПЕРШЕ ПРАВИЛО: весь контент українською

Технічні ідентифікатори (`--flag`, `VAR_NAME`, `/command`, шляхи файлів) залишаються як є.
Всі описи, назви підрозділів, коментарі — виключно українською.
Приклад: `claude -p` / `--print` | Одноразовий вивід (non-interactive) | —

---

> **Файли категорій знаходяться в піддиректорії `categories/`.** Завжди використовуйте шлях `docs/kb/categories/<file>.md`, а не `docs/kb/<file>.md`. meta.md, index.md та references/ лежать у `docs/kb/` корені.
> **Архівні версії файлів** лежать у `categories/archived/` (снапшоти з попередніх архіви). Активний файл завжди має фіксоване ім'я (напр. `cli.md`), архів — `archived/cli_v2.1.207.md`. Для пошуку по всій історії використовуйте Grep з path=`docs/kb/categories/`.

## Workflow

### Step 1: Визначити що нового

Прочитай `docs/kb/meta.md` — `last_processed` це точка відліку.

Якщо meta.md не існує — це перший запуск, насідай KB з `docs/CLAUDE-CODE-OPTIONS-GUIDE.md` (див. "First-Time Setup" внизу).

Реліз-ноти надходять від: вставка в чат, `/release-notes` output, або шлях до файлу.

### Step 2: Розібрати та категоризувати

Прочитай `references/category-map.md` (тільки зараз, один раз — вона мала).
Пройди кожну нову версію (від last_processed + 1 до останньої згаданої).
Розподіли зміни по категоріях.

Якщо щось не вписується в одну категорію — обери найбільш релевантну.
Якщо зміна стосується кількох категорій — додай в кожну.

### Step 2.5: Сформувати план IO

⚠️ **Не читай файли категорій масово!** Замість цього:

1. Сформуй список `affected_categories = []` на основі Step 2
2. Додай туди `references/anglicisms.md` (потрібен у Step 3 при формуванні описів та опціонально в Step 4.5)
3. Для кожної категорії з `affected_categories`:
   - `Grep("^## ", file)` — знайти назви всіх секцій та їхні рядки
   - Визначити цільову секцію для вставки (за назвою або найостаннішою версійною секцією)
   - `Read(offset=рядок_цільової_секції, limit=50)` — прочитати лише хвіст секції
   - `Grep("ідентифікатор", file)` — перевірка на дублікати
4. Відкривай кожен файл категорії **лише для часткового читання** під час редагування в Step 3

Це економить контекст і запобігає завантаженню файлів цілком.

### Step 3: Оновити файли категорій

Для кожної зміненої категорії:

1. Прочитай поточний файл (тільки зараз, коли додаєш в нього)
2. **Перевір на дублікати** — перед додаванням шукай запис з тим самим ідентифікатором + версією. Якщо знайшов — пропусти
3. Додай нові записи в **кінець відповідного підрозділу** (не в кінець файлу)
4. Формат: `| `identifier` | Опис українською | X.Y.Z |`
5. При депрекації: ~~закреслення~~ або `[ЗАСТАРІЛО]` замість видалення
6. Сортуй по версії (нові внизу)

Формат таблиць та приклади — див. `references/file-formats.md` (читай on-demand, один раз перед першим редагуванням).

⚠️ **При формуванні опису кожного запису** — перевіряй текст на анґліцизми (англійський корінь + українське закінчення через дефіс, напр. "invoke-є", "match-ила"). Див. `references/anglicisms.md` за таблицею замін та списком прийнятих IT-позичок. Якщо заміна невідома — використовуй прийняту позичку (кешувати, рендерити, стрімити тощо).

### Step 4: Валідація

Після оновлення всіх файлів, пройдися по списку фічей з release notes:
- Кожна згадана фіча повинна мати відповідний запис у KB
- Якщо щось загубилося — додай
- Якщо Windows-фіга — перевір що є запис і в windows.md і в основній категорії

### Step 4.5: Перевірка на анґліцизми

Після додавання нових записів перевір **лише нові записи** на анґліцизми — див. `references/anglicisms.md` (grep-патерн, таблиця замін, список прийнятих позичок).

⚠️ **Не скануй весь файл** — grep по цілому файлу тягне збіги з старих записів, створюючи шум у контексті. Варіанти:
- **Візуальна перевірка** під час Step 3 (рекомендовано) — описи пишуться вручну, анґліцизми малоймовірні якщо свідомо уникається
- **Grep з обмеженням на версійну секцію** — шукати тільки після рядка `## ... (X.Y.Z)` де X.Y.Z = поточна версія

### Step 5: Створити снапшот релізу

Файл `docs/kb/releases/YYYY-MM-DD_vX.Y.Z.md`:
```markdown
# Реліз X.Y.Z — YYYY-MM-DD
## Нові можливості
## Виправлення
## Важливі зміни
```

Якщо оброблено кілька версій — окремий файл на кожну.

### Step 6: Оновити meta.md та index.md

- `meta.md`: оновити `last_processed`, додати запис в Processing History
- `index.md`: **завжди** оновити заголовок — дата (`last_updated`) та версія (`last_processed`). Список категорій оновити лише якщо додали нову категорію

### Step 7: Звіт користувачу

Коротко: які версії оброблено, скільки записів по категоріях, чи є депрекації.

### Step 8: Резюме нового функціоналу

Після звіту виведи окремий блок із **значущим новим функціоналом** — лише те, що дійсно нове, а не виправлення чи покращення існуючого. Критерії:

- Нові команди, змінні середовища, CLI прапорці, підрозділи в settings.json
- Нові інструменти, нові типи хуків, нові категорії можливостей
- Нові інтеграції або кардинально нові поведінки (не "виправлено X", не "покращено Y")

Формат — пронумерований список з коротким описом що нового та версією:

```
1. **`команда` або назва** (X.Y.Z) — що це робить
2. **`змінна`** (X.Y.Z) — для чого
```

Якщо нових фіч немає (лише fix-и) — виведи "Нових можливостей немає, лише виправлення."

Не включай: rename/refactor записів, fix-и, change-и до існуючого, security fix-и (хіба що це нова security-змінна чи policy).

### Step 9: Архівування (лише за командою користувача)

⚠️ Архівування НЕ запускається автоматично під час обробки релізу. Лише коли користувач дає команду `заархівуй <категорія|все> до <версії>`.

Для кожної вказаної категорії (або всіх 12 при `все`):
1. Зібрати з робочого `categories/<cat>.md` всі notes ≤ X (базові з `—` трактувати як найстаріші).
2. Перше архівування категорії (відсутній `archived/<cat>_v*.md`): створити `archived/<cat>_vX.md` = кумулятив (заголовок + блокquote + базові секції + всі версійні ≤ X, відсортовані за версією).
3. Наступне (останній `archived/<cat>_v<prev>.md` існує): створити `archived/<cat>_vX.md` = приріст (заголовок + блокquote + версійні prev+1…X).
4. Очистити робочий `categories/<cat>.md` до шаблону:
   ```
   # <заголовок категорії>

   > Архів (notes до X): [archived/<cat>_vX.md](archived/<cat>_vX.md)
   > Тут — notes починаючи з версії X+1
   ```
5. Оновити `meta.md`: рядок категорії в `## Архівування` → `vX`, `archived/<cat>_vX.md`.

Пошук по всій історії: `Grep(pattern, path="docs/kb/categories/")` шукає по робочих + `archived/`.

## First-Time Setup

Якщо `docs/kb/` не існує:
1. Створи структуру директорій (включаючи `categories/archived/`)
2. Заповни початковими даними з офіційної документації `code.claude.com/docs` (прочитай сторінки docs, розбий зміст по секціях категорій)
3. Створи `meta.md` з `last_processed` = версія, включно до якої виконано початкове заповнення (без записів архівування — вони додаються при першому архівуванні в Step 9)
4. Створи `index.md` з вказівниками на категорії
5. Нічого не видаляти — всі дані зберігаються

## Rules

- **ВСЕ описи — українською** (ідентифікатори як є)
- **Без анґліцизмів** — див. `references/anglicisms.md` (grep-патерн, таблиця замін, прийняті позички)
- **Не видаляти записи** — лише додавати або позначати [ЗАСТАРІЛО]
- **Перевіряти дублікати** перед додаванням (ідентифікатор + версія)
- **Валідувати повноту** — кожна фіча з release notes = запис у KB
- **Один запис на рядок/рядок таблиці**
- **Тег версії обов'язковий** — `(X.Y.Z)` у кожному записі
- **Windows записи** → windows.md + основна категорія з тегом [Win]
- **Не читати файли повністю** — слідуй Step 2.5: Grep + частковий Read для кожної категорії. References читай on-demand як вказано в їхніх steps
- **meta.md = джерело істини** для оброблених версій
- **Зберігати стиль форматування** існуючого файлу
- **Архівування** — лише за командою користувача. Поріг рядків відсутній
- **Пошук в архіві** — `Grep(pattern, path="docs/kb/categories/")` шукає в усіх піддиректоріях, включаючи `archived/`
